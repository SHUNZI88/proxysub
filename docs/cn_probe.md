# 中国出口节点实测（沙箱侧运行手册）

本手册是定时任务「中国出口节点实测轮」的执行依据。脚本 `scripts/cn_probe.py`
与仓库同版本发布，改进脚本即改进实测行为（git pull 即生效）。

## 1. 任务定位

CI（GitHub Actions，美国出口）每轮产出「拟交沙箱待测节点文档」，本任务从
中国出口（湖南机房）实测筛选，通过者覆盖发布为主资产——解决「美国能通、
国内不通」的节点混入订阅的难题。

## 3. 单轮流程

1. **自检**：沙箱直连探测（baidu / api.github.com）。失败即中止——避免把
   沙箱自身故障误判为节点全失效；
2. **轮次闸门**：下载上轮 `verification_report.json` 取 `tested_round`（已测
   轮次）；下载 `pending_probe.json` 取 `round_id`——不同即新轮次，**立即测**
   （文档只是节点清单，活性由实时拨测决定，年龄不是新鲜信号）；相同则轮询
   等待新轮次至多 **20 分钟**（受任务 1800s 超时约束）；等不到则仅测
   carryover——未测轮次顺延至下一实测轮，不丢失。首轮无报告时任何现有
   文档都算新轮次；
3. **测试集** = carryover（当前主资产，滚动携带+自清洁）∪ pending（待测
   文档）∪ rescue（救援文档，CI 淘汰但静态可行的节点）；
4. **预算裁剪**（截止时间感知）：按剩余预算（1800s − 预留 300s − 已耗时）
   折算可测节点上限 `int(预算 ÷ 1.0s/节点)`，按**优先级填充**裁剪——
   carryover 最高优先、pending 次之、rescue 最低（本轮 0/100 通过，产能低）；
   未测节点由 CI 下轮待测文档从当前候选池重新生成时再现，**不丢失**。
   预算耗尽（上限=0）时返回空集，main() 据此跳过本轮、保留上一轮已发布
   验证集，硬保 1800s 任务超时不被击穿。见 §6。
5. **拨测**：mihomo external-controller delay API，`generate_204`
   （HTTPS+204 双信号），12 并发，失败重试一次；
6. **证据收集**（2026-10-21 合并，任务#91）：通过节点**单次切组 + 8 路
   并行**收集出口证据（cip.cc → ipip → ip-api，取首个成功）与 AI 可达性
   （chatgpt/claude/gemini/copilot/openai_api 状态码）；统一预算 120s
   （`EVIDENCE_BUDGET_S`），仅留痕、不构成闸门。合并前是两个顺序循环
   （各 120s、各覆盖一半节点）；单请求有线程级硬超时（GEO socket 5s /
   AI 8s，硬截断 +2s）——urllib socket timeout 是每次 recv 超时，龟速
   节点上的滴流响应实测可拖到 24s+（见 §9.4）；
7. **AI 可达性判据**：任何 HTTP 响应（含 403/401/302）算可达，
   api.openai.com 非 403 算 API 层可用；**不构成闸门**——AI 不可达的
   节点仍是可用代理，仅排序沉底。判据与已知坑见 §9；
8. **合并发布**：通过节点按「AI 可用性 > 双 vantage 强者 > 延迟」排序
   （订阅顺序即用户可见性顺序），构建 clash/sing-box/v2ray/proxies-only
   四格式，覆盖发布到主资产（p_* 随机名，**订阅永久地址不变**），并发布
   `verification_report.json`；
9. **轮转**：本轮消费的待测文档备份为 `pending_probe.prev.json`。

## 6. 1800s 预算加固（截止时间感知测试集上限）

定时任务超时硬顶 1800s。本轮实测 1193 节点端到端 902s（拨测约
0.62s/节点）；但轮询等待最多 20min（1200s）会挤占预算，最坏
1200+902=2102s **击穿超时**。措施：

- 常量：`TASK_BUDGET_S=1800`、`PUBLISH_RESERVE_S=300`（2026-10-21 重算：
  真实流量 ~24s + 证据收集 ≤120s + 多格式输出/发布/收尾 ~60s ≈ 204s，
  合并证据段后由 360s 降回 300s）、`PER_NODE_S=1.2`（实测 0.62s/节点
  取悲观 ×2；2.0 过度保守曾误裁 413 节点，见 §8.1）；
- `cap_test_set(nodes, budget_s)`：按优先级填充裁剪，保留集规模恒
  `≤ int(budget_s / PER_NODE_S)`，硬保不超时；
- 优先级：carryover > pending > rescue（rescue 产能低、未测节点由 CI 下轮
  文档自然再现，不丢失）；
- 预算耗尽（上限=0）返回空集 → main() 跳过本轮、保留上一轮已发布验证集；
- 实测推演（悲观 1.0s/节点）：常态（无轮询）1193 节点不裁剪，总耗时约
  1234s；最坏（轮询占满 20min）裁剪至 290 节点，总耗时恒 ≤1800s。

## 8. 看门狗与 cron 保活（L2，2026-10-20 固化）

2026-10-20 事故：cron 服务未运行 → 实测中断 → 验证陈旧超 24h → CI 兜底
把候选集覆盖主资产，质量闸门失效数小时。除「多重触发」（L1/L3/L4）外，
把保障固化为**看门狗制度**：

| 组件 | 职责 |
|---|---|
| `scripts/cron_watchdog.py` | 每 2h 一拍：① `pgrep -x cron` 查守护进程，死亡则 `service cron start` 拉起；② 距最后活动（cron.log / 验证报告 mtime 较大者）超 **8h**（槽间隔 6h + 宽限 2h）判定漏跑，经单实例锁补测一轮；③ 状态写 `/tmp/cn_probe/watchdog.log`（滚动 500 行）与 `watchdog_state.json` |
| `scripts/install_cron.sh` | 幂等安装/修复 crontab（L1+L2 两条标记块）。沙箱重建、cron 丢失、看门狗报「拉起失败」后一条命令恢复 |

设计约束：看门狗**不碰仓库任何状态文件**；任何异常吞掉记日志、退出码恒 0
（自身失败不污染 cron 邮件）；补测冷却 3h（失败风暴最密每 3h 一次）；
全新环境（无活动记录）不补测——首轮交由定时槽或人工触发。

```bash
# 手动巡检（只报告不动作）
python3 scripts/cron_watchdog.py --dry-run
# 恢复 cron 槽位（沙箱重建后）
bash scripts/install_cron.sh
```

已知局限（需人工）：cn_probe 进程**卡死**（mihomo 僵尸）时，看门狗只能
观察到「活动停滞」，补测会被单实例锁挡回——需人工 `pkill -f cn_probe.py`
后由下一拍补测。卡死识别与处置刻意不做自动化：误杀正在跑的实测轮代价
高于漏跑（漏跑有 L3/L4 兜底，误杀没有）。

### 8.1 事故记录：看门狗补测路径 bug + cron 休眠死亡（2026-10-21）

**事故链**：10-20 凌晨最后一轮实测成功后，沙箱休眠杀死 cron 服务
（开机自启启用着，但休眠恢复不重启服务）→ 四个定时槽全部静默 →
看门狗 12:17 拍检测到漏跑（活动 8.8h 前）并触发补测，但补测命令路径
拼错（`repo_root / CN_PROBE.name` 只剩基名、丢掉 `scripts/` 目录），
每次都是 `can't open file .../proxysub/cn_probe.py` 退出码 2——
**看门狗自上线起从未成功补测过一轮**（单测只断言了返回码、没断言
命令路径形状）→ 报告陈旧超 24h → CI 兜底把 140 个未测试候选节点
覆盖主资产，订阅质量静默降级。

**修复**（commit 见文末 git log）：
1. `run_catchup` 路径改为 `repo_root / "scripts" / CN_PROBE.name`；
2. 回归测试 `test_run_catchup_uses_full_script_path` 锁死命令路径形状
   （endswith `scripts/cn_probe.py` 且文件真实存在）；
3. `service cron start` 恢复服务；AGENTS.md 新增铁律第 5 条：
   补偿机制必须实测验证补偿路径本身、且须知其自身依赖（看门狗跑在
   cron 上，cron 死看门狗也死——真正不依赖本机 cron 的只有 L3）。

**待办（架构层）**：L3 WorkBuddy 云端自动化补跑目前只是设计文档中的
一层，未经验证其真实存在与可用；沙箱休眠杀死本机 cron 的问题会复发
（每次休眠都会）。彻底解法二选一：把实测主循环迁到不休眠的云端
Runner，或把 L3 落实为可观测、可验证的真实任务。

## 9. AI 可达性探测（2026-10-20 新增，不构成闸门）

### 9.1 背景：29 节点平稳的真因之一——AI 盲区

订阅有效节点数长期停在 29，沙箱诊断（v1→v2）定位到三层原因，AI 盲区是
既有闸门的设计缺口：

| 诊断事实（29 个已发布节点） | 数字 |
|---|---|
| 任一 AI 域有 HTTP 响应 | 15～16 |
| **对全部 5 个 AI 域均无响应** | **13** |
| 沙箱直连基线（验证测试有效性） | chatgpt/copilot 不可达、claude 302、gemini 不可达——测试本身有效 |

既有闸门只验证 Google 连通（generate_204）与 Cloudflare 下载，对
「能否连 AI」完全盲视：约一半已发布节点对中国用户实际不可用于 AI 连接。

### 9.2 判据（v1 诊断实测踩坑后确立）

| 判据 | 定义 |
|---|---|
| `ai_reachable` | 任一 AI 域有 **HTTP 响应**（含 403/302/401） |
| `ai_api` | `api.openai.com` 返回 **非 403**（典型 401 无密钥响应）⇒ API 层未被区域封锁 |

- chatgpt.com 403 = Cloudflare 区域拦截（网页端被拒），**≠** API 不可用；
  api.openai.com 401 = 无密钥的正常响应，是「真 AI 可用」的最强信号。两者
  必须分开记录、不可互推。

### 9.3 v1 诊断的三个方法学错误（修复记录，防复踩）

1. **`mode:"global"` 使 select 组不生效**——所有流量同一出口，29 行结果全同、
   country 全 China 是铁证；必须 `mode:"rule"` + `MATCH,PROBE`；
2. **`curl -f` 把 403/404/401 吞成失败**——必须捕获状态码，任何响应都算
   「有响应」（生产用 urllib 的 `HTTPError.code` 路径，见
   `_http_status_via_proxy`）；
3. **探针 URL 路径不当**——早期用 `/cdn-cgi/trace`，非 Cloudflare 站点
   （gemini/copilot）没有该路径，404 被误读为「不可达」；一律用站点根路径。

### 9.4 成本与边界

- 仅对终筛通过节点执行（约 30 个）：**单次切组 + 8 路并行**（GEO 3 源 +
  AI 5 域），节点间串行（共享 PROBE 选择器，并发切组会互相踩）；
- 2026-10-21 合并（任务#91）：原 GEO 与 AI 是两个顺序循环、各 120s 预算，
  手动轮实测每循环各覆盖一半通过节点——**一半节点没有 AI 数据**，排序时
  按「未知」沉底，有效节点被埋。合并为 `node_evidence`（一次切组 + 8 路
  并行）后同预算覆盖率达 54%（15/28，旧实现 AI 50%+GEO 28% 且总耗时
  240s → 合并后 122s）；
- **单请求线程级硬超时**（`_hard_timeout_call`）：urllib socket timeout
  是每次 recv 超时而非整体超时——实测龟速节点上 gemini 302 链耗时
  24.31s（socket timeout 仅 8s），单节点均摊 10.5s、120s 只覆盖 13/28。
  GEO socket 5s / AI 8s、硬截断各 +2s；GEO 收紧不丢证据（三源并行取
  首个成功，且 GEO 仅信息性留痕）；
- 统一预算 `EVIDENCE_BUDGET_S=120s`；耗时上界 真实流量 ~24s + 证据
  ≤120s + 发布 ~60s ≈ 204s < `PUBLISH_RESERVE_S` 300s，不击穿任务超时；
- **不设硬闸门**：AI 不可达不是节点死亡，节点仍是可用代理——仅排序沉底
  （`verified_rank`：AI API 可用 > AI 可达 > 无数据 > 原双 vantage 序）。

### 9.5 报告字段（增量，CI 侧只读既有键、不受影响）

- `counts.ai`：`{probed, reachable, api_ok, by_domain}`——每轮 AI 盲区
  量化，供后续源级反哺（哪些源产的节点 AI 可用率高）；
- `counts.by_source[*]`：2026-10-21 起（任务#92）在 `{tested, passed}`
  之外扩出 `{ai_tested, ai_reachable, ai_api}`——分源 AI 证据口径
  （只覆盖有 ai 数据的通过节点；无证据记 0 而非缺键）。CI 侧
  `evolution.update_source_scores_ai` 据此折回 `source_scores.json` 的
  `ai_*` 字段（只在 `ai_tested>0` 时写、不抹零），接入候选晋升 AI 优先
  与拨测复合倾斜（cn×AI 相乘封顶 2.0，任务#94，2026-10-21 完成）；
- `nodes[].ai`：`{codes, reach, ai_reachable, ai_api}` 逐节点证据；
- `dimensions.ai`：语义说明（与 us_ok/cn_ok 并列的第三测量维度）。

> 发布成功**——旧资产自然衰竭。

### 10.1 断点续跑（`probe_checkpoint.json`）

- **原先**：拨测结果只在内存 dict 里。进程被沙箱休眠杀掉即**整轮白跑**，
  下一轮 2 小时后从头再来，实测产能被反复清零；
- **现在**：逐节点增量落盘（初筛/终筛分阶段，节流 15s，原子写
  `tmp + os.replace`）。重启时按**测试集签名**（节点名集合的 SHA1 前缀）
  复用，只补测剩余节点；
- **边界**：签名不符 / 超过 `PROXYSUB_CHECKPOINT_TTL_S`（默认 45 分钟）/
  文件损坏 → 一律当作没有检查点；成功走完发布流程后 `clear()` 删除，
  **绝不让下一轮复用上一轮结论**（活性必须由实时拨测决定）；
- **代价**：多一次小文件 I/O；写失败静默降级为「重跑」，行为与修复前一致。

### 10.2 守护决策统一到 `scripts/round_guard.py`

三个入口（`cron_supervisor.sh`、`cron_watchdog.py`、`wake_trigger.py`）此前
各写一套冷却/存活判定，其中两处**错在同一处**：把「开跑」当成「完成」。

| 判据 | 旧（v3） | 新（v4） |
|---|---|---|
| 新鲜度 | `.last_round_start` 的 mtime（开跑前就 touch） | `main_asset_published_at`（上次**成功发布**） |
| 冷却 | 固定 2 小时，失败也照罚 | 连续失败指数退避 10→20→40→80→120 分钟，**资产刷新即清零** |
| 存活 | `pgrep -f "scripts/cn_probe.py"` | 探测 `cn_probe.lock` 的 flock，并读持锁者 `pid=/round=` |

`pgrep` 的两个坑都真实发生过：① **自匹配**——调用方命令行自身含该字符串，
把 shell 自己判成「已在跑」，于是根本没起新轮；② **冻结误判**——沙箱休眠是
SIGSTOP/冻结而非 kill，冻结进程仍在进程表里，`pgrep` 照样返回 0，守护永远
认为「已有实例在跑」，永不补跑。

命令行（供 shell 与 HTTP 端点共用，策略只有一份）：

```bash
python3 scripts/round_guard.py status         # 人读状态：龄期/锁/退避/决策
python3 scripts/round_guard.py decide         # 退出码 0=该跑 1=不跑，原因打 stdout
python3 scripts/round_guard.py note-attempt   # 记录尝试起点（快照当时发布戳）
python3 scripts/round_guard.py note-result --rc 0   # 成败按「资产是否刷新」判，不看 rc
```

**回归防线**：`tests/test_round_guard.py::test_guardians_do_not_reintroduce_pgrep_or_start_mark`
直接扫守护源码的可执行部分，禁止 `pgrep -f` 与 `.last_round_start` 复辟。

## 11. 本机家宽实测（任务#121，2026-11-05）

> 动机不是"换台机器跑"，而是**消灭一整类误判**：项目一路记录的
> 「沙箱测着活、本地用着死」「沙箱路径与家宽不等价」，根源都是测量点不在
> 用户真实网络上。把实测搬到用户自己家宽，这道系统性偏差直接消失。

### 11.1 需要解掉的四个绑定

| 绑定 | 沙箱形态 | 本机（Windows）形态 | 解法 |
|---|---|---|---|
| mihomo 二进制 | `mihomo-linux-amd64-vX.gz` + `gunzip` | `mihomo-windows-amd64-compatible-vX.zip`（v3 需 AVX2，老 CPU 崩） | `mihomo_asset()` 按平台选产物；`_extract_mihomo()` 用标准库 zip/gzip，不再依赖外部命令 |
| GitHub 读写 | `gh` CLI | 无 `gh` | `scripts/gh_compat.py`：有 gh 用 gh，没有走 REST（上传=先删同名再 POST） |
| 单实例锁 | `fcntl.flock` | Windows 无 fcntl | `scripts/xlock.py`：POSIX flock / Windows `msvcrt.locking` 统一 |
| 下载通道 | github.com 直连正常 | 直连**拉不动**（20s 内 0 字节） | `PROXYSUB_GH_MIRRORS` 镜像回退（默认 ghfast.top / gh-proxy.com），仅用于**公开资产**，API 与带 token 请求绝不走镜像 |

### 11.2 本机实测怎么跑

```bash
# 手动一轮（不发布，先验证链路）
python scripts/cn_probe.py --dry-run --budget 900 --max-wait 3

# 定时一轮（受 round_guard 决策：资产龄期 / 指数退避 / 锁探测）
python scripts/local_round.py --budget 1800

# 状态自查
python scripts/round_guard.py status --workdir <workdir>
```

Windows 任务计划程序定时（每小时，与沙箱 6 轮/天的节律对齐靠决策层控制）：

```
schtasks /create /tn proxysub-cn-probe /sc hourly /mo 1 /f ^
  /tr "python D:\path\to\proxysub\scripts\local_round.py"
```

### 11.3 与沙箱的关系

* **vantage 标签可区分**：报告 `vantage` 默认 `cn-hn-sandbox`，本机用
  `PROXYSUB_VANTAGE=cn-home` 覆盖——两个 vantage 的通过率必须分开统计，
  否则"沙箱 3%、家宽 10%"这种关键证据会被混成一个数字；
* **不冲突**：两边都用同一把 `cn_probe.lock`？不——两个 vantage 各自有自己的
  workdir，锁互不相干；谁发布谁持有主资产由报告里的 `main_asset_published_at`
  决定（CI 侧 `verification_fresh` 只看新鲜度）；
* **家宽优先**：当两边都在跑时，家宽的结论更接近用户实际体验；沙箱保留作
  冗余（家宽断网/关机时不断供）。

## 12. 数量与体验的平衡：填充节点剔除（任务#126，2026-11-05）

> 事故形态与前几次不同：这次不是「节点少」，而是**用户反馈 36 个里超时 6~10 个
> （数目不定）**。数量上去了，体验下来了——根源是上一轮把「能握手」当成了「能用」。

### 12.1 因果证据

把 2026-11-05 18:51 那轮的发布集（36 个）按实测流量重新分档：

| 分档 | 数量 | 用户端表现 |
|---|---|---|
| 拉满 4MB 测速上限 | 20 | 全部可用（含 ·慢 档，能持续转发） |
| 未满额但 ≥1MB | 7 | 多数可用 |
| **「延迟 >1500ms 且 <1MB」** | **7** | **与用户报的 6~10 个超时几乎一一对应** |

反例必须写下来，否则下一个人会把规则做歪：

* **HK 829KB / 561ms**、**A🟢HK 763KB / 628ms** 在客户端**正常**——
  流量小不等于不能用。所以判据是「慢」**且**「弱」，单看任一项都会误杀；
* ·慢 档里 **IT 3539ms / 4096KB** 也可用——慢但能持续转发，这正是 ·慢 档的用意。

机理：128KB 只证明握手成功、首包能回，**不证明能持续转发**。客户端一次性测全部
节点时，这类节点第二个请求就没响应，于是「有时超时、有时不超时」——这也解释了
为什么用户报的数目会「不定」。

### 12.2 规则

`is_filler_node()`（纯函数）+ 6.68 终审（放在所有提级动作之后，一处规则）：

```
延迟 > FILLER_MAX_LATENCY_MS(1500ms) 且 最好一源 < FILLER_MAX_BYTES(1MB)
  → 退回第二资产，不进主资产
```

放在 6.6 / 6.65 之后而不是塞进各自的筛选条件里：提级入口有两个，逐处加条件
一定会漏一处；终审只有一份规则，新增提级入口时自动受约束。

### 12.3 代价与边界

* **代价**：发布数会从 36 降到 29 左右。这是**有意为之**——用户要的是「有效节点」，
  超时的节点在客户端等于不存在，还会污染 url-test 的自动选择；
* **边界**：判据用的是家宽探针的延迟（探测目标是 google robots.txt）。若将来发现
  该目标本身抬高延迟，阈值要随之校准，不能照搬 1500ms 这个数——
  `_exp_delay_url.py` 就是为此准备的对照脚本。

### 12.4 顺带查出的第四个测量缺陷：延迟初筛并发虚高

调规则前先验判据本身，结果查出延迟数是假的。同一批节点两套数对照：

| 节点 | 初筛（16 路并发） | 串行复测 |
|---|---|---|
| ITA #5 | 4486ms | 2780ms |
| ITA #3 | 4341ms | 2104ms |

并发初筛时本地要同时承载 16 条到不同代理的 TLS 握手，RTT 被自家突发抬高。
危害不是「数字难看」，而是**下游全吃这个数**：3000ms 高延迟降级、1500ms 填充
剔除、报告里的延迟，都在拿被污染的量判案——阈值调得再细也是错的。

改法：`serial_latency_recheck()` —— 初筛只负责「通不通」（保持并发），过筛者
串行复测一次并**覆盖**延迟。串行反而失败的保留初筛值（一次抖动不是变快的证据）。
代价约 90s/轮（开关 `SERIAL_LATENCY_RECHECK`）。

这条与 11.1 的「并发自伤」是同一类错误的两个层面：**吞吐被并发压塌**（终筛）、
**延迟被并发抬高**（初筛）。同一个原因，两次都先在数据里看见，才想起是自家探针。

## 13. 尺子错了，不是规则错了（任务#128，2026-11-05）

用户第二次反馈：28 个里 7 超时 + 1 失败。前三次修的都是**规则**（用户池免测、
并发自伤、慢且弱、并发虚高），这次查出来是**尺子**。

### 13.1 症状

客户端能用的节点显示 75~604ms，而我对同一批节点报 283~2221ms——差 3~4 倍。
按我的尺子判「≤3000ms 可用」的节点，客户端超过一半直接超时。

### 13.2 对照实验（`_exp_delay_url.py`）

同批节点、同机、串行、每个目标采两次取最小：

| 探测目标 | 中位延迟 | 备注 |
|---|---|---|
| `https://www.google.com/robots.txt` | **1660ms** | 一直在用的尺子 |
| `https://www.gstatic.com/generate_204` | 1568ms | 仍是 Google 基础设施 |
| `http://www.msftconnecttest.com/...` | 1449ms | |
| **`http://cp.cloudflare.com/generate_204`** | **549ms** | **与客户端显示对齐** |

结论：google 对数据中心 IP（免费节点大量部署在 IDC）系统性偏慢，且带 TLS
握手，测出来的是「到 Google 的手感」而不是「到互联网的手感」。

### 13.3 改动与换算

尺子换小 3 倍，阈值必须同步换算，否则等于把闸门整个放松：

| 常量 | 旧（google 尺） | 新（cf-204 尺） | 说明 |
|---|---|---|---|
| `GENERATE_204` | google robots | cf-204 | 探测器 |
| `CN_MAX_PUBLISH_LATENCY_MS` | 3000 | 1500 | 主闸门 |
| `USABLE_MAX_LATENCY_MS` | 3000 | 1500 | 可用档 |
| `AI_PROMOTE_MAX_LATENCY_MS` | 3000 | 1500 | AI 提级 |
| `FILLER_MAX_LATENCY_MS` | 1500 | 1000 | 慢且弱 |

### 13.4 结果

订阅 23 个，**延迟中位 561ms、最大 1482ms、20 个 ≤1000ms**，AI API 可用 22/23。
数量比上一轮少 5 个，但延迟第一次和用户在客户端看到的数字同量级。

### 13.5 这是同一类错误的第五次

| # | 缺陷 | 表现 |
|---|---|---|
| 1 | 用户池免测特权 | 7 天旧证据直接发 |
| 2 | 终筛并发 6 路 | 吞吐被自家压塌，好节点判「先快后断」 |
| 3 | 可用档门槛 128KB | 只证明握手，不证明能持续转发 |
| 4 | 初筛并发 16 路 | RTT 被抬高，闸门判据被污染 |
| 5 | **探测目标 google** | **尺子本身偏慢 3 倍** |

共同点：**先怀疑节点，再怀疑规则，最后才怀疑测量**。所以立一条操作纪律：
**「我测的数与用户看到的不一致」时，第一动作是对照实验，不是调阈值。**

## 14. 单样本判定 = 赌运气（任务#129，2026-11-05）

用户第三次反馈：23 个里 2 超时 + 1 失败。这轮没换规则、没换尺子，只改**采样数**。

### 14.1 诊断

对已发布的 23 个各连测 5 次（串行、cf-204、单次探测）：

| 通过次数 | 数量 | 含义 |
|---|---|---|
| 5/5 | 18 | 稳定 |
| 4/5 | 3 | 偶发掉线 |
| 2/5、1/5 | 2 | 基本废，却因「单次恰好成功」混进主资产 |

此前每个节点只采一次样本，一次成功就放行——等于掷一次骰子决定要不要发。

### 14.2 一个差点让闸门白做的坑

第一版闸门用的是 `delay_test` 采样，结果 23 个节点**全部 5/5**。原因：
`delay_test` 失败会自动重试一次（5s→8s），偶发失败被重试洗成成功——
测的正是「偶发」，却用了会掩盖偶发的工具。

改法：新增 `delay_once()`（单次、3s 超时、不重试），闸门专用。
附带收益：失败样本 3s 返回而非 5+8=13s，一轮反而更快。

### 14.3 规则与结果

```
连测 5 次（delay_once）→ 成立次数 ≥ 4 才算稳定
延迟 = 成功样本的中位数（不是最小值：最小是运气最好那一次）
```

本轮：49 个过初筛 → **15 个不稳定被剔除（30%）** → 终筛 23 → 发布 **20 个**。
延迟中位 566ms、最大 1448ms、14 个 ≤800ms，AI API 可用 18/20。

### 14.4 一条规律

今天六次修正，前五次都在改「怎么判」，这次是改「判几次」：

| # | 缺陷 | 一句话 |
|---|---|---|
| 1 | 用户池免测 | 旧证据直接发 |
| 2 | 终筛并发 6 | 吞吐被自家压塌 |
| 3 | 门槛 128KB | 握手成功 ≠ 能持续转发 |
| 4 | 初筛并发 16 | 延迟被自家抬高 |
| 5 | 探测目标 google | 尺子本身偏慢 3 倍 |
| 6 | **单样本判定** | **判一次 = 赌运气** |

共同点：**判据的可靠性取决于它承受过多少次推翻它的尝试**——采样一次、
并发一次、用一个目标测一次，都是没被推翻过的结论。

## 15. 淘汰机制审计：六处单向删除（任务#130，2026-11-06）

> 用户反馈「订阅源仓库锐减」。审计结论：**不是某一条规则太严，而是六处淘汰
> 都是单向的**——删掉的东西再也回不来，于是任何一次判据偏差都会永久沉淀。

### 15.1 全链路淘汰点与可逆性

| # | 淘汰点 | 判据来源 | 可逆性（修复前） | 修复后 |
|---|---|---|---|---|
| 1 | 静态协议闸门 | 白名单 + 结构校验 | 改代码才可逆 | 不变（本就与测量无关） |
| 2 | 源降级 official→removed | 4 通道，其中 3 条吃实测 | 30 天冷却 + 需被重新发现 | **判据版本化，旧判决自动失效并回迁** |
| 3 | 候选拒绝 candidates→rejected | `no_stable_contribution` 等 | 30 天冷却 + 重新发现 | **同上，且可主动回炉** |
| 4 | 延迟初筛失败 | delay API | **永久失联**（不进任何资产） | **全量写库，按轮转复测** |
| 5 | 稳定性/延迟/填充闸门 | 实测 | 进第二资产，可回炉 | 不变（第二资产本就回炉） |
| 6 | 节点库裁剪 | `last_pass` 超 30 天 | 通过过但近期没过 → 被清 | **改按 `last_seen`** |

### 15.2 实证数字（修复前）

* official 源：**6 / 上限 30**；removed 34 条，其中
  `cn_low_pass_rate 19 + zero_unique_contribution 5 + zero_real_ok 3 = 27 条`
  依赖 CN 实测；
* 候选源：candidates 3 个、rejected **65** 个（`no_stable_contribution` 39 条）；
* 节点库：**74 条**，而 cn_history 记着 **1257 个**「曾经通过过」的指纹——
  意味着 90% 以上的历史可用节点，配置已经彻底丢失。

### 15.3 三条修复原则

1. **判据版本化**：判决记录带 `mv`；判据升级（本次 `MEASUREMENT_VERSION=2`，
   因为修了探测尺子/并发/采样/门槛四处）后，依赖实测的旧判决自动失效。
   与尺子无关的判决（诱饵转载、蜜罐篡改、抓取失败）保持原判——它们不因
   测量方式改变而变。
2. **回收优先于删除**：装不下的回迁源留在 `removed` 里排队，不因上限而丢弃；
   候选同理，回炉受 `limit` 约束而不是清空。
3. **全量留痕 + 轮转复测**：本轮测过的**所有**节点都写库（含失败），
   记 `last_seen/fails`；加载按「通过次数优先、同档最久未测优先」并设
   `NODE_LIBRARY_RETEST_H=6` 静默期。否则高通过次数的节点会每轮占满 60 个名额，
   库再大也只有同一小批在循环。

### 15.4 为什么这类问题会反复出现

淘汰规则每收紧一次（可用档、填充剔除、稳定性闸门），池子就少一批；
六次修正里有五次是**收紧**，而**回收通路一条都没有**。规则可以严，
但**回收必须存在**——否则系统只有减量、没有增量，最终一定收敛到个位数。

一句话：**判据可以错，判决不能不可逆。**

## 16. 「测速有数据但用不了」的真正原因（任务#131，2026-11-06）

用户反馈：FlClash 刷新到 24 个节点，几乎全是意大利，测速有数据但实际无法使用。

### 16.1 先纠正我自己的一次误判

第一版实验脚本用 `mode: global` + `MATCH,PROBE`——**global 模式下规则不生效**，
所有流量走 GLOBAL 选择器，切换 PROBE 完全空转。于是 40 个节点全部呈现
「google/youtube/chatgpt 不通、github 通」的同一副面孔，我据此判成「运营商免流
白名单节点」。实际上那是**直连的中国出口**在测。**结论作废。**

用生产同款 `mode: rule` 重测，出口 IP 立刻变成 IT / FR，google 204、youtube 200。
教训：`global` 与 `rule` 的行为差异足以让整份实验结论反过来；凡「所有样本表现
完全一致」，先怀疑测量环境，而不是先怀疑节点。

### 16.2 真实数据（rule 模式，逐节点切组，24 个已发布节点）

| 指标 | 结果 |
|---|---|
| 能上 google (204) | 20 / 24 |
| 能上 youtube (200) | 20 / 24 |
| **chatgpt.com 非 403** | **0 / 24** |
| api.openai.com 非 403 | 20 / 24 |
| 全指标失败（香港 vless 4 个） | 4 / 24 |

结论有两层：

### 16.3 我们自己的判据错在哪

原来的「AI 可用」判据是 `ai_api = openai_api != 403`。它测的是 **API 端点**，
而用户在浏览器里打开的是 **chatgpt.com 网页**——两者结论相反：API 401 判「可用」，
网页 403 实际打不开。所以历史上那些「AI API 可用 30/31」的报告是**真的**，
但它回答的不是用户的问题。

### 16.4 本次改动

* `SITE_TARGETS`（google / youtube / github）+ `usability_verdict`：至少 2/4 有
  HTTP 响应才算「能上网」（403 也算——说明 TLS 通了）；
* **`·无AI` 后缀**：chatgpt.com 403 的节点打标，不剔除（免费池里 AI 网页干净的

## 19. 停更 10 小时：死代理伪装成「token 失效」（任务#134，2026-11-08）

用户要求「再全面检查发布一轮」。检查发现**线上资产停在 10 小时前**，而定时
任务从 19:14 起每小时都「启动」、从不「结束」。

### 19.1 两个独立故障，叠在一起让问题不可见

**故障一（真正的停更原因）**：用户级环境变量 `PROXYSUB_GH_PROXY` 指向
`http://127.0.0.1:7890`（当初为 gh 授权配的本地代理），而该代理早已退出。
`gh` 在代理连不通时**把网络错误报成**：

```
X Failed to log in to github.com account SHUNZI88 (keyring)
  - The token in keyring is invalid.
```

复现确证：手动给 gh 加上这个死代理，立刻复现同样的报错；去掉代理、直连
`api.github.com` 则一切正常（token 一直是好的）。于是每轮都在鉴权处熔断，
`exit 3`，资产不刷新——**看起来像凭据坏了，实际是代理没了**。

**故障二（让故障一隐身）**：`local_round` 把子进程输出写文件时按 UTF-8 读，
而 Windows 子进程默认按 cp936 写中文——解码抛异常，**吃掉了后面的「结束」
记录与 `note_result`**。于是日志里只剩一串「启动」，守护状态停在旧值，
6 轮失败一个字的解释都没有。

### 19.2 修复

* `gh_compat.effective_proxy()`：配置的代理先做端口连通性探测（0.6s，带缓存），
  **连不通就直连并只告警一次**。判据落在「端口能不能连」上，不信 gh 的措辞；
  作用点覆盖 gh 子进程、REST、镜像下载三处；
* `local_round`：子进程强制 `PYTHONIOENCODING=utf-8`，读日志用
  `errors="replace"`——任何编码异常都不再能吃掉轮次结果；
* 保留 `PROXYSUB_GH_PROXY` 配置（代理起来时自动启用），但不再让它成为单点。

## 19. 订阅「无内容」：主资产被上传失败打空（任务#135，2026-11-19）

### 19.1 现象与直接原因

客户端刷新订阅提示无内容。直接检查 Release 资产清单：

```
p_58dd290962_d.yaml / _p.yaml / _s.json / _v.txt   ← 都在
p_58dd290962_c.yaml                                ← 不存在
```

客户端订阅地址指向 `_c.yaml`，因此 404。而轮次日志写的是「已刷新 3/4 个格式
资产」，看起来"只是少了一个"，实际是**主资产没了**。

### 19.2 四个根因

| # | 根因 | 后果 |
|---|---|---|
| 1 | `--clobber` 语义是「先 DELETE 旧资产、再 POST 新的」 | 一次 POST 失败即打空线上文件 |
| 2 | 资产名从现网列表**反推**而非**计算** | 主 clash 一丢就永远"跳过"，自锁 |
| 3 | 工作目录在 `%TEMP%` | 被系统清理：mihomo 重下 10 分钟、报告丢失、守护判龄期 999h |
| 4 | gh 子进程 stdout 未指定编码（cp936 读 UTF-8） | 线程内解码异常 → 空 stdout，鉴权/列表时好时坏 |

第 4 条还解释了另一个怪现象：`local_round` 读子进程日志时解码失败抛异常，
把「结束」记录与 `note_result` 一起吃掉——所以 19:14 之后 6 轮定时任务
只留下「启动」，守护状态停在旧值，看不出任何轮次结果。

### 19.3 修复

* **非破坏性上传**：先传 `<name>.staging` 并校验大小，再替换正式名；
  暂存失败绝不触碰现网文件（宁可不更新，也不能打空）。
* **发布后自校验 + 自愈**：四格式 + 报告必须在线且非空，缺则补传（3 轮退避）；
  主 clash 仍缺失 → 本轮退出码 5，让守护按失败重试，而不是静默 404。
* **资产名确定性生成**：`FMT_ASSET` + 前缀兜底；一个 `p_*` 都不剩时仍能重建。
  前缀解析必须用 `^(p_[0-9a-f]+)_`——`ASSET_RE` 的分组是格式代码不是前缀，
  取错会生成垃圾资产（本次真发生过 `c_d.yaml`）。
* **工作目录迁出 `%TEMP%`** → `%LOCALAPPDATA%\proxysub`，并从旧目录自动复制状态。
* 全部 gh 子进程 `encoding="utf-8", errors="replace"`；子进程日志强制 UTF-8。

### 19.4 一条操作纪律

**「上传成功」不等于「线上真的有」。** 发布链路的最后一步必须是**回读校验**：
列一次资产清单、比一次大小。本次事故从 11-18 起就存在，期间每轮都"成功"
上报，直到用户刷新订阅才发现。

## 21. 「检测存活但连不上」——判据缺了 TTFB（任务#137，2026-11-19 夜）

### 21.1 用户判断是对的

「就算检测存活到实际并不能正常连接」。按客户端方式复核（加载**发布出去的
那个文件**、逐节点切 `🚀 节点选择`、4 个真实站点）后，20 个节点中 7 个
「通过」，但它们的 TTFB 是：

```
2373ms / 6170ms / 6935ms / 7475ms / 7961ms …
```

**8 秒才返回一个 204，在浏览器里就是一直转圈。** 而我的判据是
「8~10 秒内有没有 2xx/3xx」——只判有无响应，不判多快响应。

### 21.2 直连对照：不是家里网络的问题

同机直连（不经节点）TTFB 中位：gstatic **148ms**、baidu 97ms、cloudflare 571ms。
所以经节点 2~8 秒是节点侧，不是家宽拥塞。

### 21.3 夜间池子的真实状态（23:30~00:08）

| 阶段 | 数量 |
|---|---|
| 候选（实时抓取） | 832 |
| 探活通过（5s 单次） | 73 |
| 双判据（状态 + TTFB≤2500ms）通过 2 次 | 10 |
| 延迟 ≤1500ms 且吞吐 ≥64KB/s | **0** |

73 个探活节点的 TTFB 分布：最小 1069ms、中位 **2841ms**、P90 4254ms；
2000ms 以内只有 7 个。**这个时段的免费池子客观上是 2~4 秒级。**

### 21.4 改动

| 项 | 旧 | 新 |
|---|---|---|
| 直测超时 | 10s | **3s** |
| 通过判据 | 状态 2xx/3xx | 状态 + **TTFB ≤ 2500ms** |
| 复测语义 | 连续 2 次都过 | 最多 3 次尝试**累计过 2 次** |
| 排序 | 速率 | **TTFB 优先**（用户第一感受是"多久有反应"） |
| 鉴权失败 | 直接熔断 | **重试一次**（夜间 TLS 抖动会被 gh 报成 token 超时） |
| 触发方式 | 只看资产龄期 | 每小时**健康抽查**，TTFB 达标数 <1/3 则提前重发 |

健康抽查实测（00:20，对当前这份 20 个节点）：抽查 4 个、可用 3 个、
TTFB 中位 1835ms —— 说明这份列表「能用但慢」，不是全死；也说明单次测量
方差很大，必须多次采样才能判断列表状态。

### 21.5 结论与边界

* 免费公开源在**晚高峰到凌晨**的可用质量是 2~4 秒级，这不是筛选能解决的；
* 白天（15:25 那轮）同一套源能出 20 个 542ms 中位的节点——**发布时机显著影响结果**；
* 想稳定拿到 1 秒内、可持续使用的节点，只有付费/私有源这条路。

## 22. 「几乎都是意大利节点」——供给同质化、错误指标与通道不稳（任务#138，2026-11-20）

### 22.1 现象

用户连续三轮反馈「近几轮发布的节点几无可用了」。把已发布产物摊开看：

| 指标 | 值 |
|---|---|
| 发布节点数 | 36 |
| 唯一服务器 | **17**（36 个节点只落在 17 台机器上） |
| 协议 | ss 26 / vless 8 / anytls 2 |
| 端口 | **19999 占 25 个** |
| 地区 | 意大利 22 个（61%） |

发布集里 86% 是 carryover（上一轮已发的旧节点，31/36）。新血只有 5 个。

### 22.2 第一层证据：源在同质化，不是在枯竭

12 个正式源全量抓取，去重后只有 **756 个唯一节点、533 个唯一 host:port**，
其中 **306 个 host:port 被 2 个以上源重复收录**。即：这些「独立源」大半在
复读同一批机器。典型形态是一个 /24 里 23 个存活节点、全是 ss:19999、
跨 6 个源出现——各源给同一台机器起了不同随机 host 名，fingerprint 含 host
因而互不相同，去重完全失效，一台物理机被算成十几个「唯一节点」。

### 22.3 第二层证据：通过的节点高度集中在意大利

同一轮 841 个测试集按地区切开：

| 地区 | 进入测试 | 通过目标直测 | 通过率 |
|---|---|---|---|
| 意大利 | 38 | 23 | **60.5%** |
| 非意大利 | 803 | 31 | **3.9%** |

而供给分布是分散的（美国 210、德国 93、英国 65、新加坡 48、香港 35、日本 34）。
所以「满屏意大利」不是取样偏，是**只有这批意大利机器真在跑**——它们是同一家
共享机场的入口，几十人共用一个端口，沙箱独占测速好看，用户端一拥塞就超时。

### 22.4 第三层证据（关键反证）：TCP 存活不是指标

按「边际新增 × TCP 存活率」给外部源排序，第一名是 anaer/Sub：
边际新增 1039 个、TCP 存活 52.5%。但目标站实测结果是 **0/12**——
隧道能建立（baidu 200）、墙外站全不通。它 11-11 被淘汰时的判决是
`cn_low_pass_rate:0/159`，**那个判决是对的**。

同一批实测（阳性对照 = 当前已发布资产 3 个，3/3 全通，证明测量可信）：

| 源 | 隧道通 | chatgpt | youtube |
|---|---|---|---|
| 对照·已发布 | 3/3 | 3 | 3 |
| FlyingDashie/Free-node-autotest | 12/12 | 7 | 6 |
| bily1258-design/beimi | 12/12 | 4 | 3 |
| anaer/Sub | 12/12 | 0 | 0 |
| happygithub007/nodelist | 11/12 | 0 | 0 |

结论：**源评估的唯一有效指标是「目标站可达率」，TCP 存活率会选出大量僵尸。**

### 22.5 第二个根因：GitHub raw 通道本身不稳

一次轮次里 14 个源有 13 个抓取失败、测试集只剩 156 个、新血通过 0 个。
同时刻单独测：

```
raw.githubusercontent.com        3 次 → 1 次 200，另 2 次卡满 19s 后 code=000
gcore.jsdelivr.net/gh/…@main/…   200，183KB，2.1s
cdn.jsdelivr.net/gh/…@main/…     200，183KB，7.5s
```

**抓取失败不是源失效，是通道失效。** 现在每个 GitHub 源都有三条通道
（raw → gcore jsDelivr → cdn jsDelivr），逐条回退。

### 22.6 改动

| 项 | 旧 | 新 |
|---|---|---|
| 初筛物理去重 | 无（只在发布侧限 3/服务器） | **进测试集前**：同 server ≤2、同 /24 ≤3 |
| 抓取去重 | 仅 fingerprint（含 host） | 追加 **server:port** 级去重 |
| 抓取通道 | 仅 raw，失败即弃 | raw → **jsDelivr ×2** 回退，staging 上传重试 |
| 抓取总时限 | 90s | 150s（三通道需要两批） |
| 单机发布上限 | 3 | **2** |
| 地区发布上限 | 25 | **12** |
| 配置加载 | 直接启动，坏节点整轮熔断 | 启动前 **`mihomo -t` 预检**，自动剔除非法节点 |
| 上传校验 | 一次性读资产大小 | 轮询至稳定（API 列表有延迟，曾误判「暂存校验不符」） |
| 晚高峰 | 照跑 | 22:00–01:00 且资产 < stale+8h 时**避让** |
| 新并入源 | — | FlyingDashie、bily1258/beimi（均经目标站实测验证） |

离线核算初筛去重代价：756 个唯一节点按 server≤2、/24≤3 保留 563 个（74.5%
名额），仍覆盖 78% 的 TCP 活节点，且保留的活节点里 vless 占 85%（ss 从 27 压到 7）。

### 22.7 边界

* 免费公开源的真实可用供给，客观上就是**一家意大利共享机场的几十台机器**
  被多个源反复复读。扩大源数量不改变这个结构，只有实测能分辨。
* 物理限流会让发布数量下降，但换来的是「分散在不同机器上」——比同一批机器
  堆数量更耐久。
* 想稳定拿到非欧洲、低延迟、可持续的节点，仍然只有付费/私有源这条路。

## 23. 增量供应：源准入改成目标站实测（任务#139，2026-11-20）

### 23.1 命中率的真实量级

一次性把 21 个候选源全部实测（每源 8~12 个 TCP 活样本，经 mihomo 打 chatgpt.com）：

| 源 | 边际新增 | TCP 存活 | 目标站可达 |
|---|---|---|---|
| anaer/Sub | 1039 | 52.5% | **0/12** |
| happygithub007/nodelist | 267 | 65.0% | **0/12** |
| 10ium ×3 | 142 / 58 / 41 | 32~40% | **0/24** |
| proco2024 ×2 | 62 / 42 | 46~65% | **0/16** |
| moneyfly1 / rzhy1 / peacefish / youkai / redeyehare | 300+ | 5~10% | **0/33** |
| FlyingDashie/Free-node-autotest | 173 | 54.3% | **7/12** |
| bily1258-design/beimi | 557 | 50.0% | **4/12** |

**命中率约 2/21 ≈ 10%。** 且 TCP 存活率完全无预测力——65% 存活的那个 0 可用，
54% 存活的那个 7/12 可用。

推论：增量供应只能是「批量筛 + 每源实测」。每次只看两三个源，期望产出不到
0.3 个，永远补不上；而正式轮次只有 1500 个名额，让未验证的源进来就是拿预算赌运气。

### 23.2 工具：scripts/source_trial.py

流程：抓取（多通道）→ TCP 筛 → **延迟闸门** → 目标站实测 → 达标才写入 official。

三条判定线（缺一不可）：

* **样本充足**（≥5）：实测出现过某源 TCP 只筛出 1 个活节点、1/1 命中，
  按比率 100%，实际是源已基本全死；
* **可达率**（≥25%）；
* **绝对可用数**（≥2）：比率再高，只有 1 个也补不上供给。

结果写 `source_trial.json` 台账，已验过的源不再重复烧预算。
候选来自 `candidate_pool.json`——由扫描脚本的**真实抓取成功记录**固化。

调度：Windows 计划任务 `proxysub-source-trial`，每日 13:40 验 6 个源。

### 23.3 两个被实证推翻的判断

**（一）选源与用源必须是同一把尺子。**

首版工具跳过延迟闸门，只测「TCP 活 → chatgpt」。FlyingDashie 因此被测成
7/12 可用。但同一批节点进入正式轮次后：**该源 97 个节点 0 通过**——它们
全部倒在 delay 初筛（`TARGET_LATENCY_MAX_MS=1500`）。
正式轮次的链路是「TCP → delay 达标 → 目标直测」，选源若少一道闸门，
选出来的源在正式轮次里贡献为零。已在 `run_batch` 里补上 `delay_once` 判定。

**（二）小样本的 25% 是噪声。**

`0xRadikal` 与 `alireza786786` 各测 8 个、各 2 个可用（25%，刚好压线），
按旧判据被转正。随后一轮正式拨测：`0xRadikal` 78 个 0 通过、
`alireza` 121 个 0 通过——**占掉 199 个测试名额、零产出**。
两源已从 official 移除并记入 `removed`（理由 `trial_misjudged`）。
8 个样本的 95% 置信区间是 [7%, 59%]，用它做准入本就不该给结论；
这也是后来把 `--min-samples` 提高到 5 并同时要求绝对可用数的原因。

### 23.4 候选池的教训

首版工具在代码里手写了 40 个「业界常见源」。实测前三个全部失效：

```
barry-far/V2ray-Configs        → 403 Repository access blocked（ToS，2025-05）
yebekhe/TelegramV2rayCollector → 404 Not Found
Epodonios/v2ray-configs        → 404 Not Found
```

仓库名必须来自**真实抓取成功的记录**，不能凭印象写。候选池因此改为由扫描
脚本产出、固化成 `candidate_pool.json`。

### 23.5 边界

* 免费公开源里，能过「延迟 1.5s + 目标站可达」的节点比例，客观上是**个位数
  百分比**。把源数量翻倍，期望产出也只是翻倍，不会跃升。
* 因此「17 个左右不重复」很可能是免费源的稳态上限；要突破只能换供给类型
  （付费/私有节点），而不是继续加源。

## 24. 只剩 6 个节点：三个根因与一次结论更正（任务#140，2026-11-20）

### 24.0 先更正上一节的结论

第 23.5 节写过「17 个左右很可能是免费源的稳态上限，再突破只能换供给类型」。
**这个结论是错的**，而且错的方式很典型：它是我拿被自己污染过的输入算出来的
上限，却被当成了外部世界的上限。

推翻它的证据在下面。一句话概括：那 12~15 个不是供给上限，是**解析层丢包 +
源选错 + 观测环境错配**三者叠加的结果。

### 24.1 根因一：解析层静默丢包（最致命，也最隐蔽）

现象：v2rayfree 一条订阅 36 条链接，只解析出 26 个，缺的 10 个全是 ss：

```
ss://YWVzLTI1Ni1nY206…@202.50.253.45:19999?#DE SS-22 | free-nodes
                                        ↑ 空查询串
```

`hostport.rsplit(":", 1)` 得到 port=`"19999?"`，`int()` 抛 `ValueError`，
被外层 `except Exception: return None` 吞掉。**一条日志都没有。**

丢掉的正是 `202.50.253.x:19999` 这一批——也就是历史上反复出现「存活的全是
ss:19999」的那批节点，本机可用率最高的一类。

同类问题还有：`hysteria2://` / `hy2://` / `anytls://` 根本没有解析器。
kooker 单源 696 条链接里有 40 条 hy2、1 条 anytls，一律丢弃。

修复后同源同刻复测：

| 源 | 修复前 | 修复后 |
|---|---|---|
| v2rayfree | 0/8 目标站可达 | **9/15（60%）** |

> 纪律：`except Exception: return None` 用在解析器里，必须能统计到丢包。
> 现在 `scripts/diag_parse.py` 逐源比对「原文 scheme 数 vs 解析结果」，
> 任何 scheme 的缺口都会被打出来。

### 24.2 根因二：观测环境错配（抓源不该在家宽做）

原设计是「CI 抓取 + 初选，本机实测」。第 133 节为了对抗快照陈旧，把抓取搬
到了本机（国内），并加 jsDelivr 兜底。方向对（要新鲜），位置错：

* 本机抓 `raw.githubusercontent.com` 十次有两三次失败（实测同一 URL 3 次
  只有 1 次 200，失败卡满 19 秒）；
* 于是「这个源没内容」与「这个源我这边连不上」**不可区分**；
* 源的可达性评估被 GFW 噪声污染，越评越窄——被淘汰的源里混着大量其实
  完全健康的源。

修法是把职责按网络位置切开：

| 环节 | 位置 | 判断什么 |
|---|---|---|
| 抓取 / 解析 / 协议闸门 / 去重 | GitHub Actions（海外） | 源有没有内容、内容是否合法 |
| 延迟 / 目标站 / 吞吐 | 本机（家宽） | 从我这里能不能用 |

新增 `scripts/pool_build.py` + `.github/workflows/pool-refresh.yml`：
每 20 分钟抓全部源，产出 `pool.json`（滚动 Release，tag `pool`）。
本机 `load_ci_pool()` 优先消费它；只有下载失败或龄期 > `POOL_MAX_AGE_H`(4h)
才降级自抓，并显式打警告。实测 CI 侧 24 个源全部成功、3670 个候选、耗时 24s。

### 24.3 根因三：选源靠数量而不是本机产出率

同一时刻、同一判据（延迟 6s + 目标站 8s）、每源抽 15~25 个：

| 源 | 池子 | 抽样 | 目标站可达 |
|---|---|---|---|
| free-nodes/v2rayfree | 29 | 15 | **9（60%）** |
| mfuu/v2ray | 45 | 15 | **6（40%）** |
| shaoyouvip/free | 23 | 15 | **5（33%）** |
| ripaojiedian/freenode | 6 | 6 | **2（33%）** |
| Pawdroid/Free-servers | 13 | 13 | 2（15%） |
| ermaozi/get_subscribe | 222 | 15 | 1（7%） |
| kooker/FreeSubsCheck | 345 | 15 | 1（7%） |
| free18 / chengaopan / Au1rxx / mahdibland / lanzm | 239~1525 | 各 15 | **0** |

规律非常清楚：**小池子、人工筛选、几小时一更的源，产出率 33~60%；
「聚合器的聚合器」大池子（几百到上千节点）产出率 0~7%**。

而改造前的 14 个源里，有 5 个正是后者，却按节点数分走了大部分拨测名额。
这就是「测了 311 个节点 0 通过」的来源。

改动：

1. 新增 10 个源（含 19.9k star 的 Pawdroid、kooker、mfuu、v2rayfree、free18、
   yy1588133、xyfqzy、Au1rxx 等），官方源 14 → 24；
2. `pool_sample()` 按**逐源历史产出率**分配名额：
   * 新源保底 `POOL_MIN_PER_SRC`(20) 个——否则它永远没有历史、永远拿不到
     名额，形成自我实现的淘汰；
   * 余量按 `(passed+1)/(tested+20)` 加权，单源上限 45%；
   * 已测满 60 个仍 0 通过的源，上界收紧到探针级（3~5 个），探索不归零但
     代价随证据递减；
3. 每轮把 `counts.by_source` 折回 `source_yield.json`（历史按 0.7 衰减）。

### 24.4 附带修掉的一个致命静默失败

分片 mihomo 实例没有配置预检。一个 `2022-blake3-chacha20-poly1305` 节点
密码是 URL 编码（`…%3D`）且长度不合规，mihomo 直接：

```
level=fatal msg="Parse config error: proxy 119: ss 47.85.162.44:443 cipher: … illegal base64 data"
```

6 个分片全部启动失败，`start_shards` 静默返回空列表，整轮零产出，日志里
只有一句「mihomo 未就绪」。两处修复：

* 解析层：2022 系列密钥先 unquote，再按 cipher 要求校验长度（16/32 字节），
  不合格直接丢弃；
* 启动层：分片在**启动前统一跑一次** `mihomo -t`（复用 `prune_invalid_cfg`），
  剔除非法节点；失败时日志写明是哪个实例、看哪个 m.log。

### 24.5 边界（这次写清楚验证方式）

* 24 个源里 11 个的抽样产出率仍是 0，但**样本只有 15 个**：95% 置信上界是
  14%，不能据此断言「此源永久无效」。判定要等 `source_yield.json` 累计
  到 60 个样本。
* Pawdroid 的 2/13 与 v2rayfree 的 9/15 之间有显著差异（33% vs 60% 的区间
  重叠），「小池子更好」目前是**趋势**而非定论，需要下一轮更大样本复核。
* 免费节点寿命以小时计，所以池子必须持续刷新；`pool-refresh` 每 20 分钟
  一轮，但 GitHub 计划任务可能延迟数分钟，龄期闸门按 4h 兜底。
