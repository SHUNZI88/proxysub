# 中国出口节点实测（沙箱侧运行手册）

本手册是定时任务「中国出口节点实测轮」的执行依据。脚本 `scripts/cn_probe.py`
与仓库同版本发布，改进脚本即改进实测行为（git pull 即生效）。

## 1. 任务定位

CI（GitHub Actions，美国出口）每轮产出「拟交沙箱待测节点文档」，本任务从
中国出口（湖南机房）实测筛选，通过者覆盖发布为主资产——解决「美国能通、
国内不通」的节点混入订阅的难题。

## 3. 单轮流程

1. **自检**：沙箱直连探测（baidu / api.github.com）。失败即中止——避免把
   沙箱自身故障误判为节点全失效；
2. **轮次闸门**：下载上轮 `verification_report.json` 取 `tested_round`（已测
   轮次）；下载 `pending_probe.json` 取 `round_id`——不同即新轮次，**立即测**
   （文档只是节点清单，活性由实时拨测决定，年龄不是新鲜信号）；相同则轮询
   等待新轮次至多 **20 分钟**（受任务 1800s 超时约束）；等不到则仅测
   carryover——未测轮次顺延至下一实测轮，不丢失。首轮无报告时任何现有
   文档都算新轮次；
3. **测试集** = carryover（当前主资产，滚动携带+自清洁）∪ pending（待测
   文档）∪ rescue（救援文档，CI 淘汰但静态可行的节点）；
4. **预算裁剪**（截止时间感知）：按剩余预算（1800s − 预留 300s − 已耗时）
   折算可测节点上限 `int(预算 ÷ 1.0s/节点)`，按**优先级填充**裁剪——
   carryover 最高优先、pending 次之、rescue 最低（本轮 0/100 通过，产能低）；
   未测节点由 CI 下轮待测文档从当前候选池重新生成时再现，**不丢失**。
   预算耗尽（上限=0）时返回空集，main() 据此跳过本轮、保留上一轮已发布
   验证集，硬保 1800s 任务超时不被击穿。见 §6。
5. **拨测**：mihomo external-controller delay API，`generate_204`
   （HTTPS+204 双信号），12 并发，失败重试一次；
6. **证据收集**（2026-10-21 合并，任务#91）：通过节点**单次切组 + 8 路
   并行**收集出口证据（cip.cc → ipip → ip-api，取首个成功）与 AI 可达性
   （chatgpt/claude/gemini/copilot/openai_api 状态码）；统一预算 120s
   （`EVIDENCE_BUDGET_S`），仅留痕、不构成闸门。合并前是两个顺序循环
   （各 120s、各覆盖一半节点）；单请求有线程级硬超时（GEO socket 5s /
   AI 8s，硬截断 +2s）——urllib socket timeout 是每次 recv 超时，龟速
   节点上的滴流响应实测可拖到 24s+（见 §9.4）；
7. **AI 可达性判据**：任何 HTTP 响应（含 403/401/302）算可达，
   api.openai.com 非 403 算 API 层可用；**不构成闸门**——AI 不可达的
   节点仍是可用代理，仅排序沉底。判据与已知坑见 §9；
8. **合并发布**：通过节点按「AI 可用性 > 双 vantage 强者 > 延迟」排序
   （订阅顺序即用户可见性顺序），构建 clash/sing-box/v2ray/proxies-only
   四格式，覆盖发布到主资产（p_* 随机名，**订阅永久地址不变**），并发布
   `verification_report.json`；
9. **轮转**：本轮消费的待测文档备份为 `pending_probe.prev.json`。

## 6. 1800s 预算加固（截止时间感知测试集上限）

定时任务超时硬顶 1800s。本轮实测 1193 节点端到端 902s（拨测约
0.62s/节点）；但轮询等待最多 20min（1200s）会挤占预算，最坏
1200+902=2102s **击穿超时**。措施：

- 常量：`TASK_BUDGET_S=1800`、`PUBLISH_RESERVE_S=300`（2026-10-21 重算：
  真实流量 ~24s + 证据收集 ≤120s + 多格式输出/发布/收尾 ~60s ≈ 204s，
  合并证据段后由 360s 降回 300s）、`PER_NODE_S=1.2`（实测 0.62s/节点
  取悲观 ×2；2.0 过度保守曾误裁 413 节点，见 §8.1）；
- `cap_test_set(nodes, budget_s)`：按优先级填充裁剪，保留集规模恒
  `≤ int(budget_s / PER_NODE_S)`，硬保不超时；
- 优先级：carryover > pending > rescue（rescue 产能低、未测节点由 CI 下轮
  文档自然再现，不丢失）；
- 预算耗尽（上限=0）返回空集 → main() 跳过本轮、保留上一轮已发布验证集；
- 实测推演（悲观 1.0s/节点）：常态（无轮询）1193 节点不裁剪，总耗时约
  1234s；最坏（轮询占满 20min）裁剪至 290 节点，总耗时恒 ≤1800s。

## 8. 看门狗与 cron 保活（L2，2026-10-20 固化）

2026-10-20 事故：cron 服务未运行 → 实测中断 → 验证陈旧超 24h → CI 兜底
把候选集覆盖主资产，质量闸门失效数小时。除「多重触发」（L1/L3/L4）外，
把保障固化为**看门狗制度**：

| 组件 | 职责 |
|---|---|
| `scripts/cron_watchdog.py` | 每 2h 一拍：① `pgrep -x cron` 查守护进程，死亡则 `service cron start` 拉起；② 距最后活动（cron.log / 验证报告 mtime 较大者）超 **8h**（槽间隔 6h + 宽限 2h）判定漏跑，经单实例锁补测一轮；③ 状态写 `/tmp/cn_probe/watchdog.log`（滚动 500 行）与 `watchdog_state.json` |
| `scripts/install_cron.sh` | 幂等安装/修复 crontab（L1+L2 两条标记块）。沙箱重建、cron 丢失、看门狗报「拉起失败」后一条命令恢复 |

设计约束：看门狗**不碰仓库任何状态文件**；任何异常吞掉记日志、退出码恒 0
（自身失败不污染 cron 邮件）；补测冷却 3h（失败风暴最密每 3h 一次）；
全新环境（无活动记录）不补测——首轮交由定时槽或人工触发。

```bash
# 手动巡检（只报告不动作）
python3 scripts/cron_watchdog.py --dry-run
# 恢复 cron 槽位（沙箱重建后）
bash scripts/install_cron.sh
```

已知局限（需人工）：cn_probe 进程**卡死**（mihomo 僵尸）时，看门狗只能
观察到「活动停滞」，补测会被单实例锁挡回——需人工 `pkill -f cn_probe.py`
后由下一拍补测。卡死识别与处置刻意不做自动化：误杀正在跑的实测轮代价
高于漏跑（漏跑有 L3/L4 兜底，误杀没有）。

### 8.1 事故记录：看门狗补测路径 bug + cron 休眠死亡（2026-10-21）

**事故链**：10-20 凌晨最后一轮实测成功后，沙箱休眠杀死 cron 服务
（开机自启启用着，但休眠恢复不重启服务）→ 四个定时槽全部静默 →
看门狗 12:17 拍检测到漏跑（活动 8.8h 前）并触发补测，但补测命令路径
拼错（`repo_root / CN_PROBE.name` 只剩基名、丢掉 `scripts/` 目录），
每次都是 `can't open file .../proxysub/cn_probe.py` 退出码 2——
**看门狗自上线起从未成功补测过一轮**（单测只断言了返回码、没断言
命令路径形状）→ 报告陈旧超 24h → CI 兜底把 140 个未测试候选节点
覆盖主资产，订阅质量静默降级。

**修复**（commit 见文末 git log）：
1. `run_catchup` 路径改为 `repo_root / "scripts" / CN_PROBE.name`；
2. 回归测试 `test_run_catchup_uses_full_script_path` 锁死命令路径形状
   （endswith `scripts/cn_probe.py` 且文件真实存在）；
3. `service cron start` 恢复服务；AGENTS.md 新增铁律第 5 条：
   补偿机制必须实测验证补偿路径本身、且须知其自身依赖（看门狗跑在
   cron 上，cron 死看门狗也死——真正不依赖本机 cron 的只有 L3）。

**待办（架构层）**：L3 WorkBuddy 云端自动化补跑目前只是设计文档中的
一层，未经验证其真实存在与可用；沙箱休眠杀死本机 cron 的问题会复发
（每次休眠都会）。彻底解法二选一：把实测主循环迁到不休眠的云端
Runner，或把 L3 落实为可观测、可验证的真实任务。

## 9. AI 可达性探测（2026-10-20 新增，不构成闸门）

### 9.1 背景：29 节点平稳的真因之一——AI 盲区

订阅有效节点数长期停在 29，沙箱诊断（v1→v2）定位到三层原因，AI 盲区是
既有闸门的设计缺口：

| 诊断事实（29 个已发布节点） | 数字 |
|---|---|
| 任一 AI 域有 HTTP 响应 | 15～16 |
| **对全部 5 个 AI 域均无响应** | **13** |
| 沙箱直连基线（验证测试有效性） | chatgpt/copilot 不可达、claude 302、gemini 不可达——测试本身有效 |

既有闸门只验证 Google 连通（generate_204）与 Cloudflare 下载，对
「能否连 AI」完全盲视：约一半已发布节点对中国用户实际不可用于 AI 连接。

### 9.2 判据（v1 诊断实测踩坑后确立）

| 判据 | 定义 |
|---|---|
| `ai_reachable` | 任一 AI 域有 **HTTP 响应**（含 403/302/401） |
| `ai_api` | `api.openai.com` 返回 **非 403**（典型 401 无密钥响应）⇒ API 层未被区域封锁 |

- chatgpt.com 403 = Cloudflare 区域拦截（网页端被拒），**≠** API 不可用；
  api.openai.com 401 = 无密钥的正常响应，是「真 AI 可用」的最强信号。两者
  必须分开记录、不可互推。

### 9.3 v1 诊断的三个方法学错误（修复记录，防复踩）

1. **`mode:"global"` 使 select 组不生效**——所有流量同一出口，29 行结果全同、
   country 全 China 是铁证；必须 `mode:"rule"` + `MATCH,PROBE`；
2. **`curl -f` 把 403/404/401 吞成失败**——必须捕获状态码，任何响应都算
   「有响应」（生产用 urllib 的 `HTTPError.code` 路径，见
   `_http_status_via_proxy`）；
3. **探针 URL 路径不当**——早期用 `/cdn-cgi/trace`，非 Cloudflare 站点
   （gemini/copilot）没有该路径，404 被误读为「不可达」；一律用站点根路径。

### 9.4 成本与边界

- 仅对终筛通过节点执行（约 30 个）：**单次切组 + 8 路并行**（GEO 3 源 +
  AI 5 域），节点间串行（共享 PROBE 选择器，并发切组会互相踩）；
- 2026-10-21 合并（任务#91）：原 GEO 与 AI 是两个顺序循环、各 120s 预算，
  手动轮实测每循环各覆盖一半通过节点——**一半节点没有 AI 数据**，排序时
  按「未知」沉底，有效节点被埋。合并为 `node_evidence`（一次切组 + 8 路
  并行）后同预算覆盖率达 54%（15/28，旧实现 AI 50%+GEO 28% 且总耗时
  240s → 合并后 122s）；
- **单请求线程级硬超时**（`_hard_timeout_call`）：urllib socket timeout
  是每次 recv 超时而非整体超时——实测龟速节点上 gemini 302 链耗时
  24.31s（socket timeout 仅 8s），单节点均摊 10.5s、120s 只覆盖 13/28。
  GEO socket 5s / AI 8s、硬截断各 +2s；GEO 收紧不丢证据（三源并行取
  首个成功，且 GEO 仅信息性留痕）；
- 统一预算 `EVIDENCE_BUDGET_S=120s`；耗时上界 真实流量 ~24s + 证据
  ≤120s + 发布 ~60s ≈ 204s < `PUBLISH_RESERVE_S` 300s，不击穿任务超时；
- **不设硬闸门**：AI 不可达不是节点死亡，节点仍是可用代理——仅排序沉底
  （`verified_rank`：AI API 可用 > AI 可达 > 无数据 > 原双 vantage 序）。

### 9.5 报告字段（增量，CI 侧只读既有键、不受影响）

- `counts.ai`：`{probed, reachable, api_ok, by_domain}`——每轮 AI 盲区
  量化，供后续源级反哺（哪些源产的节点 AI 可用率高）；
- `counts.by_source[*]`：2026-10-21 起（任务#92）在 `{tested, passed}`
  之外扩出 `{ai_tested, ai_reachable, ai_api}`——分源 AI 证据口径
  （只覆盖有 ai 数据的通过节点；无证据记 0 而非缺键）。CI 侧
  `evolution.update_source_scores_ai` 据此折回 `source_scores.json` 的
  `ai_*` 字段（只在 `ai_tested>0` 时写、不抹零），接入候选晋升 AI 优先
  与拨测复合倾斜（cn×AI 相乘封顶 2.0，任务#94，2026-10-21 完成）；
- `nodes[].ai`：`{codes, reach, ai_reachable, ai_api}` 逐节点证据；
- `dimensions.ai`：语义说明（与 us_ok/cn_ok 并列的第三测量维度）。

> 发布成功**——旧资产自然衰竭。

### 10.1 断点续跑（`probe_checkpoint.json`）

- **原先**：拨测结果只在内存 dict 里。进程被沙箱休眠杀掉即**整轮白跑**，
  下一轮 2 小时后从头再来，实测产能被反复清零；
- **现在**：逐节点增量落盘（初筛/终筛分阶段，节流 15s，原子写
  `tmp + os.replace`）。重启时按**测试集签名**（节点名集合的 SHA1 前缀）
  复用，只补测剩余节点；
- **边界**：签名不符 / 超过 `PROXYSUB_CHECKPOINT_TTL_S`（默认 45 分钟）/
  文件损坏 → 一律当作没有检查点；成功走完发布流程后 `clear()` 删除，
  **绝不让下一轮复用上一轮结论**（活性必须由实时拨测决定）；
- **代价**：多一次小文件 I/O；写失败静默降级为「重跑」，行为与修复前一致。

### 10.2 守护决策统一到 `scripts/round_guard.py`

三个入口（`cron_supervisor.sh`、`cron_watchdog.py`、`wake_trigger.py`）此前
各写一套冷却/存活判定，其中两处**错在同一处**：把「开跑」当成「完成」。

| 判据 | 旧（v3） | 新（v4） |
|---|---|---|
| 新鲜度 | `.last_round_start` 的 mtime（开跑前就 touch） | `main_asset_published_at`（上次**成功发布**） |
| 冷却 | 固定 2 小时，失败也照罚 | 连续失败指数退避 10→20→40→80→120 分钟，**资产刷新即清零** |
| 存活 | `pgrep -f "scripts/cn_probe.py"` | 探测 `cn_probe.lock` 的 flock，并读持锁者 `pid=/round=` |

`pgrep` 的两个坑都真实发生过：① **自匹配**——调用方命令行自身含该字符串，
把 shell 自己判成「已在跑」，于是根本没起新轮；② **冻结误判**——沙箱休眠是
SIGSTOP/冻结而非 kill，冻结进程仍在进程表里，`pgrep` 照样返回 0，守护永远
认为「已有实例在跑」，永不补跑。

命令行（供 shell 与 HTTP 端点共用，策略只有一份）：

```bash
python3 scripts/round_guard.py status         # 人读状态：龄期/锁/退避/决策
python3 scripts/round_guard.py decide         # 退出码 0=该跑 1=不跑，原因打 stdout
python3 scripts/round_guard.py note-attempt   # 记录尝试起点（快照当时发布戳）
python3 scripts/round_guard.py note-result --rc 0   # 成败按「资产是否刷新」判，不看 rc
```

**回归防线**：`tests/test_round_guard.py::test_guardians_do_not_reintroduce_pgrep_or_start_mark`
直接扫守护源码的可执行部分，禁止 `pgrep -f` 与 `.last_round_start` 复辟。

## 11. 本机家宽实测（任务#121，2026-11-05）

> 动机不是"换台机器跑"，而是**消灭一整类误判**：项目一路记录的
> 「沙箱测着活、本地用着死」「沙箱路径与家宽不等价」，根源都是测量点不在
> 用户真实网络上。把实测搬到用户自己家宽，这道系统性偏差直接消失。

### 11.1 需要解掉的四个绑定

| 绑定 | 沙箱形态 | 本机（Windows）形态 | 解法 |
|---|---|---|---|
| mihomo 二进制 | `mihomo-linux-amd64-vX.gz` + `gunzip` | `mihomo-windows-amd64-compatible-vX.zip`（v3 需 AVX2，老 CPU 崩） | `mihomo_asset()` 按平台选产物；`_extract_mihomo()` 用标准库 zip/gzip，不再依赖外部命令 |
| GitHub 读写 | `gh` CLI | 无 `gh` | `scripts/gh_compat.py`：有 gh 用 gh，没有走 REST（上传=先删同名再 POST） |
| 单实例锁 | `fcntl.flock` | Windows 无 fcntl | `scripts/xlock.py`：POSIX flock / Windows `msvcrt.locking` 统一 |
| 下载通道 | github.com 直连正常 | 直连**拉不动**（20s 内 0 字节） | `PROXYSUB_GH_MIRRORS` 镜像回退（默认 ghfast.top / gh-proxy.com），仅用于**公开资产**，API 与带 token 请求绝不走镜像 |

### 11.2 本机实测怎么跑

```bash
# 手动一轮（不发布，先验证链路）
python scripts/cn_probe.py --dry-run --budget 900 --max-wait 3

# 定时一轮（受 round_guard 决策：资产龄期 / 指数退避 / 锁探测）
python scripts/local_round.py --budget 1800

# 状态自查
python scripts/round_guard.py status --workdir <workdir>
```

Windows 任务计划程序定时（每小时，与沙箱 6 轮/天的节律对齐靠决策层控制）：

```
schtasks /create /tn proxysub-cn-probe /sc hourly /mo 1 /f ^
  /tr "python D:\path\to\proxysub\scripts\local_round.py"
```

### 11.3 与沙箱的关系

* **vantage 标签可区分**：报告 `vantage` 默认 `cn-hn-sandbox`，本机用
  `PROXYSUB_VANTAGE=cn-home` 覆盖——两个 vantage 的通过率必须分开统计，
  否则"沙箱 3%、家宽 10%"这种关键证据会被混成一个数字；
* **不冲突**：两边都用同一把 `cn_probe.lock`？不——两个 vantage 各自有自己的
  workdir，锁互不相干；谁发布谁持有主资产由报告里的 `main_asset_published_at`
  决定（CI 侧 `verification_fresh` 只看新鲜度）；
* **家宽优先**：当两边都在跑时，家宽的结论更接近用户实际体验；沙箱保留作
  冗余（家宽断网/关机时不断供）。

## 12. 数量与体验的平衡：填充节点剔除（任务#126，2026-11-05）

> 事故形态与前几次不同：这次不是「节点少」，而是**用户反馈 36 个里超时 6~10 个
> （数目不定）**。数量上去了，体验下来了——根源是上一轮把「能握手」当成了「能用」。

### 12.1 因果证据

把 2026-11-05 18:51 那轮的发布集（36 个）按实测流量重新分档：

| 分档 | 数量 | 用户端表现 |
|---|---|---|
| 拉满 4MB 测速上限 | 20 | 全部可用（含 ·慢 档，能持续转发） |
| 未满额但 ≥1MB | 7 | 多数可用 |
| **「延迟 >1500ms 且 <1MB」** | **7** | **与用户报的 6~10 个超时几乎一一对应** |

反例必须写下来，否则下一个人会把规则做歪：

* **HK 829KB / 561ms**、**A🟢HK 763KB / 628ms** 在客户端**正常**——
  流量小不等于不能用。所以判据是「慢」**且**「弱」，单看任一项都会误杀；
* ·慢 档里 **IT 3539ms / 4096KB** 也可用——慢但能持续转发，这正是 ·慢 档的用意。

机理：128KB 只证明握手成功、首包能回，**不证明能持续转发**。客户端一次性测全部
节点时，这类节点第二个请求就没响应，于是「有时超时、有时不超时」——这也解释了
为什么用户报的数目会「不定」。

### 12.2 规则

`is_filler_node()`（纯函数）+ 6.68 终审（放在所有提级动作之后，一处规则）：

```
延迟 > FILLER_MAX_LATENCY_MS(1500ms) 且 最好一源 < FILLER_MAX_BYTES(1MB)
  → 退回第二资产，不进主资产
```

放在 6.6 / 6.65 之后而不是塞进各自的筛选条件里：提级入口有两个，逐处加条件
一定会漏一处；终审只有一份规则，新增提级入口时自动受约束。

### 12.3 代价与边界

* **代价**：发布数会从 36 降到 29 左右。这是**有意为之**——用户要的是「有效节点」，
  超时的节点在客户端等于不存在，还会污染 url-test 的自动选择；
* **边界**：判据用的是家宽探针的延迟（探测目标是 google robots.txt）。若将来发现
  该目标本身抬高延迟，阈值要随之校准，不能照搬 1500ms 这个数——
  `_exp_delay_url.py` 就是为此准备的对照脚本。

### 12.4 顺带查出的第四个测量缺陷：延迟初筛并发虚高

调规则前先验判据本身，结果查出延迟数是假的。同一批节点两套数对照：

| 节点 | 初筛（16 路并发） | 串行复测 |
|---|---|---|
| ITA #5 | 4486ms | 2780ms |
| ITA #3 | 4341ms | 2104ms |

并发初筛时本地要同时承载 16 条到不同代理的 TLS 握手，RTT 被自家突发抬高。
危害不是「数字难看」，而是**下游全吃这个数**：3000ms 高延迟降级、1500ms 填充
剔除、报告里的延迟，都在拿被污染的量判案——阈值调得再细也是错的。

改法：`serial_latency_recheck()` —— 初筛只负责「通不通」（保持并发），过筛者
串行复测一次并**覆盖**延迟。串行反而失败的保留初筛值（一次抖动不是变快的证据）。
代价约 90s/轮（开关 `SERIAL_LATENCY_RECHECK`）。

这条与 11.1 的「并发自伤」是同一类错误的两个层面：**吞吐被并发压塌**（终筛）、
**延迟被并发抬高**（初筛）。同一个原因，两次都先在数据里看见，才想起是自家探针。

## 13. 尺子错了，不是规则错了（任务#128，2026-11-05）

用户第二次反馈：28 个里 7 超时 + 1 失败。前三次修的都是**规则**（用户池免测、
并发自伤、慢且弱、并发虚高），这次查出来是**尺子**。

### 13.1 症状

客户端能用的节点显示 75~604ms，而我对同一批节点报 283~2221ms——差 3~4 倍。
按我的尺子判「≤3000ms 可用」的节点，客户端超过一半直接超时。

### 13.2 对照实验（`_exp_delay_url.py`）

同批节点、同机、串行、每个目标采两次取最小：

| 探测目标 | 中位延迟 | 备注 |
|---|---|---|
| `https://www.google.com/robots.txt` | **1660ms** | 一直在用的尺子 |
| `https://www.gstatic.com/generate_204` | 1568ms | 仍是 Google 基础设施 |
| `http://www.msftconnecttest.com/...` | 1449ms | |
| **`http://cp.cloudflare.com/generate_204`** | **549ms** | **与客户端显示对齐** |

结论：google 对数据中心 IP（免费节点大量部署在 IDC）系统性偏慢，且带 TLS
握手，测出来的是「到 Google 的手感」而不是「到互联网的手感」。

### 13.3 改动与换算

尺子换小 3 倍，阈值必须同步换算，否则等于把闸门整个放松：

| 常量 | 旧（google 尺） | 新（cf-204 尺） | 说明 |
|---|---|---|---|
| `GENERATE_204` | google robots | cf-204 | 探测器 |
| `CN_MAX_PUBLISH_LATENCY_MS` | 3000 | 1500 | 主闸门 |
| `USABLE_MAX_LATENCY_MS` | 3000 | 1500 | 可用档 |
| `AI_PROMOTE_MAX_LATENCY_MS` | 3000 | 1500 | AI 提级 |
| `FILLER_MAX_LATENCY_MS` | 1500 | 1000 | 慢且弱 |

### 13.4 结果

订阅 23 个，**延迟中位 561ms、最大 1482ms、20 个 ≤1000ms**，AI API 可用 22/23。
数量比上一轮少 5 个，但延迟第一次和用户在客户端看到的数字同量级。

### 13.5 这是同一类错误的第五次

| # | 缺陷 | 表现 |
|---|---|---|
| 1 | 用户池免测特权 | 7 天旧证据直接发 |
| 2 | 终筛并发 6 路 | 吞吐被自家压塌，好节点判「先快后断」 |
| 3 | 可用档门槛 128KB | 只证明握手，不证明能持续转发 |
| 4 | 初筛并发 16 路 | RTT 被抬高，闸门判据被污染 |
| 5 | **探测目标 google** | **尺子本身偏慢 3 倍** |

共同点：**先怀疑节点，再怀疑规则，最后才怀疑测量**。所以立一条操作纪律：
**「我测的数与用户看到的不一致」时，第一动作是对照实验，不是调阈值。**
